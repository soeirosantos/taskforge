## Task objective

Create the Go module (`taskforge`, `go 1.23.5`) and a self-contained
`internal/jobs` domain package holding the job domain and the three job
executors (`hash`, `delay`, `fail`), plus unit tests. No SQLite, no HTTP.

Scope: `go.mod`, `.gitignore`, `internal/jobs/*.go`.

## Acceptance criteria

1. Every legal SPEC §12 transition is accepted and every illegal one rejected,
   including that COMPLETED and CANCELLED are terminal.
2. `hash` over `"hello world"` yields
   `b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9` in
   lowercase hex; the empty string succeeds.
3. A `delay` execution cancelled 20ms into a 30000ms delay returns in well under
   a second with a cancellation error.
4. `fail` always returns the `INTENTIONAL_FAILURE` error with message
   `job failed intentionally`.
5. Payload validation rejects unknown fields, missing fields, wrong types, and
   out-of-range `milliseconds`, and accepts the SPEC §7–§9 examples.
6. Marshalling a job produces exactly the SPEC §11 field set, with `null` for
   absent values.

## Unresolved failure

A single undefined identifier in a test file. `newByteReader` is referenced once
and defined nowhere:

```
internal/jobs/job_test.go:192:  dec := json.NewDecoder(newByteReader(raw))
```

The surrounding test walks the encoded JSON token stream to assert that field

acceptance criteria have been verified** — the other 1200 lines may well be
correct, but there is currently no evidence either way.

## Approaches already attempted

**Attempt 1 (sonnet).** Stopped to determine whether `json.Number` was required
to reject a non-integer `milliseconds` value, and the investigation consumed the
whole budget. Its last words were *"Let me verify Go's `json.Number` decoding
behavior for type-safety before committing to this approach."*

Before escalating, the orchestrator probed that question in a scratch module so
the escalation would not inherit it. Result: a plain `int64` field with
`DisallowUnknownFields` already rejects `100.5`, `1e3`, `5000.0` and `"5000"`, so
`json.Number` is unnecessary; the real gap is that `null` and *absent* both
decode silently to the zero value, which needs a pointer field (`*int64`). This
verified finding was handed to attempt 2, which used it.

**Attempt 2 (opus).** Consumed the resolved finding correctly and implemented the
full package, writing implementation files first and test files last. It ran out
of turns during the final test file. Its last words were *"Now the tests, one
file per acceptance area."*

Do not repeat either investigation — the payload-decoding question is settled and
recorded above.

## Assumptions or decisions requiring human input

**The root cause is a planning defect, not a worker defect, and fixing it changes
the plan — which is a human decision.**

T1 as scoped bundles module initialization, five distinct domain concerns (job
representation, state table, payload validation, executors, error codes) and test
coverage for six acceptance criteria: roughly 1200 lines. Two different models at
two capability tiers both ran out of a 15-turn budget on it, at different points.
That is strong evidence the task is simply too large for the configured bound,
and re-running the same shape a third time would likely fail the same way.

Options for the human:

1. **Split T1 and re-run** (recommended). Two tasks: (1a) domain types, state
   table, payload validation, error codes; (1b) executors plus the full test
   suite. Each is comfortably inside a 15-turn budget. The existing code is a
   sound starting point and need not be discarded.
2. **Dispatch a narrow repair task** for the single undefined helper, then judge
   T1 on the resulting verification. Cheapest path, but it treats the symptom;
   the size problem remains, and the same risk applies to T3, T5 and T7, which
   are comparably large.
3. Raise `maxTurns` for the worker profiles. **This changes the apparatus
   mid-experiment and would make this arm non-comparable to the others.** Not
   recommended without explicitly restarting the arm.

The orchestrator did **not** fix the one-line error itself. Doing so would make
it both implementer and verifier of the same code, which is the exact
self-certification the bounded-execution policy exists to prevent.
